# meilisearch — Element Decomposition and Stack Mapping

Date: 2026-07-02
Source project: `meilisearch/meilisearch` v1.48.3 (Community Edition MIT; Enterprise Edition files under BSL 1.1) — <https://github.com/meilisearch/meilisearch>
Decision: **inspiration-first, accepted 2026-07-02** — no immediate `adopt`; the search server stays out of the ecosystem runtime behind the objective adoption triggers of E16. See the 2026-07-02 entries in `decision-log.md`.
Scope: personal ecosystem ecosystem only. Professional workspaces are out of scope.
Review: **Accepted 2026-07-02** — all proposed verdicts ratified ("go all"); the five open questions are resolved below. The implementation gate is lifted for the candidate increments listed in "First increment", each behind its own factual gate.

## Why this document

Meilisearch is the sovereign search reference on our radar (Meili SAS, Paris; engine MIT; already listed as the Algolia alternative in the sovereign-stack table). Several of its elements land on declared ecosystem territory: the `gear-memory` full-text rung (ADR `adrs/0006-gear-memory-progressive-indexing.md`), the unimplemented `search` field on the feed-mind articles API, note search (`rumble-note` reads through `gear-memory`), and factory-wide search over specs/ADRs/reports. Per ADR `adrs/0022-starred-repos-strengthen-existing-repos.md`, external projects strengthen existing repositories; this document decomposes Meilisearch element by element so each concept lands on the right layer — or is explicitly rejected — instead of being adopted wholesale.

Method precedent: `codebase-memory-mcp-decomposition.md` (PR #3, accepted 2026-07-02).

## Method

Taxonomy reused from `github-stars-stack-audit.md`:

- Disposition: `adopt` (use as-is), `rebuild` (reimplement the concept on our stack), `knowledge` (reference material only), `reject`, `quarantine`.
- Layer: `rumble`, `portal`, `bolt`, `wrench`, `gear`, `cross-layer`, `outside`.

Unlike the codebase-memory-mcp exercise, no global inspiration-only decision was taken up front: the owner is explicitly open to adoption, porting, or inspiration per element. The map below therefore proposes per-element dispositions, including conditional adoption triggers where relevant.

## Reference facts (verified 2026-07-02)

- Engine: Rust workspace (~21 crates: `milli` core, `index-scheduler`, `meilisearch-auth`, `filter-parser`, `dump`, `file-store`, `meilitool`, `fuzzers`, `workloads/`, …) served over HTTP (actix-web), single binary, storage on LMDB via `heed`. Satellite crates: `charabia` (tokenizer), `heed` (LMDB wrapper), `arroy` → `hannoy` (vector store, HNSW over LMDB per upstream release notes).
- Licensing split (2026): Community Edition is MIT; files explicitly marked "Enterprise Edition (EE)" are governed by `LICENSE-EE` = Business Source License 1.1 (non-production use only without a commercial agreement; Change Date 4 years per release; Change License MIT). EE currently covers enterprise identity (SAML SSO, SCIM). BSL is banned by our license policy; the MIT CE perimeter remains compatible.
- Search features: search-as-you-type (<50 ms claim), typo tolerance (Levenshtein automata over FST word dictionaries), ordered ranking rules (`words → typo → proximity → attribute → sort → exactness`) with per-result ranking score details, filters + faceted search (dedicated `filter-parser`), geosearch, multi-tenancy via signed tenant tokens embedding forced search rules, hybrid lexical/semantic search with configurable `semanticRatio`, federated multi-index search, document relations / `_foreign` filter (beta), Dynamic Search Rules (conditional pinning with time windows, beta, v1.41.0 2026-03), conversational search (chat route, MCP/LangChain integrations), personalization (Cloud-side).
- Ops surface: durable task queue with automatic batching (`index-scheduler`), webhooks, dumps/snapshots + dumpless upgrades, offline ops tool (`meilitool`), Prometheus `/metrics`, declarative benchmark workloads (`workloads/`), fuzzed filter parser.
- Security signal: CVE-2026-57823 / CVE-2026-57824 patched in v1.48.2 / v1.47.1 — a real network attack surface, and an upstream that patches it quickly.
- Telemetry: Segment-based analytics enabled by default, opt-out via environment variable.
- Sovereignty: French company, EU-based; engine self-hostable; Meilisearch Cloud is their managed offer (out of scope for the ecosystem).

## Deep dives (implementation-relevant)

### 1. E3 + E6 — Deterministic explainable ranking for the `gear-memory` full-text rung

Meilisearch's relevance is not one opaque score: it is a **bucket sort through an ordered list of rules**, each rule splitting the candidate set further, with an API that returns per-rule score details. Transposed to the FTS5 rung (ADR 0006, rung 2 "deterministic offline search baseline"):

- keep FTS5 as the match engine, but rank through an explicit ordered cascade (e.g. exact-term > all-terms > `bm25()` > stable tiebreak on canonical id) instead of trusting `bm25()` alone;
- every hit must be able to explain its rank (which rule placed it) — the search twin of "zeros are findings";
- prefix search (`prefix=` at table creation) and `snippet()`/`highlight()` cover the search-as-you-type and highlighting surface without leaving SQLite;
- explicit truncation metadata as already ruled in P1 queries; no silent caps.

This lands as a design constraint in the future FTS-rung ADR of `gear-memory` — not as code in this lot (P1 is owned by a parallel session; the rung starts only after P1 merges).

### 2. E18 — "The credential carries the filter": Biscuit search scoping

Meilisearch tenant tokens embed the search rules (forced per-index filters) in a signed token, so the server cannot be asked to search outside the tenant's slice. The ecosystem transposition is **Biscuit attenuation**: a `search_scope` fact plus a check that forces the filter at query execution, attenuated per delegation depth per the shared Biscuit contract. This converges with `wrench-db-inspect`'s `vector_search_without_tenant_filter` rule: the same invariant ("no search without a tenant-scoped filter") enforced at the credential layer instead of only at the SQL-review layer. Activation trigger: the first multi-user search surface (`rumble-lm` sessions being the likely first case).

### 3. E20 — Curation rules for feed-mind

Dynamic Search Rules show a clean shape for editorial control: declarative rules (condition on the query or context + time window) that pin or promote documents, evaluated at query time, no reindexing. Feed-mind already has curation rules in its charter; the transferable design is: rules as data (versioned, testable), evaluated deterministically over the product DB, with rule hits visible in the response envelope. No engine adoption required.

### 4. E16 — Objective adoption triggers for the server

The server is rejected today, not forever. Adoption review triggers (any one suffices to reopen):

1. a real user-facing need for instant typo-tolerant multi-attribute search that the product DB's FTS demonstrably cannot serve (measured, not assumed);
2. index volume or latency beyond the FTS baseline on real data (benchmark evidence, per the "SQLite FTS first; benchmark Tantivy if quality/perf insufficient" ruling — Meilisearch enters that same benchmark as the served option);
3. an online-first product whose search is a core promise rather than a utility.

If triggered: self-hosted Community Edition only, MIT perimeter verified, version pinned, EE files excluded, telemetry disabled, index treated as derived/regenerable data (ADR 0026: operational substrate, never core truth).

## Alignment with existing ecosystem decisions

- **ADR 0006 (progressive indexing, Proposed)** and the 2026-06-30 ladder decision in `decision-log.md`: full-text is rung 2, deterministic offline baseline; vector is acceleration only. The rung-commutativity amendment travels with PR #3 (pending merge). Nothing here changes the ladder; E3/E6 refine rung 2's internal design.
- **"SQLite FTS first; benchmark Tantivy if quality/perf insufficient"** (`../gear/06-p0-implementation-roadmap.md`, open-questions table): honored — Meilisearch joins that future benchmark as the served-engine option (E16 trigger 2) rather than replacing the FTS-first ruling.
- **ADR 0022 (starred repos strengthen existing repos)**: honored — every verdict targets an existing repo; no new repository.
- **ADR 0023 (layer classification by client)**: factory-wide search is a Gear capability used from the factory, not a Wrench fork of it (Q2 finalizes).
- **ADR 0026 (core truth vs operational substrate)**: any search index is derived, regenerable data; a search server, if ever adopted, is operational substrate and never custodian of core truth.
- **`github-stars-stack-audit.md` cross-references**: `unum-cloud/USearch` (adopt, gear, benchmark-gated) keeps its row; E11 adds `hannoy` to the same future benchmark. Q5 proposes a retroactive audit row for `meilisearch/meilisearch` for traceability.
- **Bounded-context isolation**: E19 quarantined, mirroring the codebase-memory-mcp precedent (cross-context joins never drive design).
- **Biscuit shared contract** (`adrs/0001-biscuit-shared-delegated-authorization.md`): E18 extends it with a search-scoping pattern, demand-driven.

None shipped in this lot; the gate lifted on 2026-07-02. Candidate increments, in dependency order, each behind its own factual gate: (a) FTS5 rung design note/ADR in `gear-memory` once P1 is merged (E3+E6); (b) feed-mind `search` on its elected DB (landing map row 2, after the storage election); (c) Biscuit `search_scope` pattern note in the shared contract (E18, demand-driven — first multi-user search surface).

## Open questions — resolved 2026-07-02

1. **FTS ranking depth** → start rung 2 with **explained `bm25()` plus stable tiebreaks**; the ordered-rule cascade (E3) is introduced only if result quality disappoints. The cascade stays the documented reference design.
2. **Factory-wide search owner** → **`gear-memory` CLI multi-root read fan-out** (gear capability, factory usage per ADR 0023); revisit only if a dedicated evidence report emerges.
3. **Feed-mind sequencing** → `search` lands on the product's elected DB, **after** the storage election; no new component for a dojo.
4. **Charabia trigger** → confirmed: **real multi-script content in an indexed product**; fr/en stays the default assumption until a product says otherwise.
5. **Stars-audit traceability** → **yes**: retroactive `meilisearch/meilisearch` row added to `github-stars-stack-audit.md`, pointing at this spec.
