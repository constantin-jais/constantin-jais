# Orchestrator Lock — Input Manifest

- Status: live meta registry (control-plane ADR 0047 follow-up), created 2026-07-17
- Purpose: when the monorepo opens its composite orchestrator Specification Lock, its author must find every prepared input in one place instead of doing session archaeology. This file is that place. It is a **pointer registry, not a plan** (same discipline as `cold-backlog.md`).

## What the lock is

The monorepo blocks orchestrator work twice over (`docs/transformation/G1-WORK-PACKAGES.md`): `WP-G2-S01` "creates neither `crates/context` nor `crates/agent-orchestrator`", and Missions (`WP-G3-A01`) "remains blocked from orchestrator integration until a separate human-approved **execution-plan, control-protocol and agent-harness** Specification Lock exists" (`work-packages.v1.json`, global constraints). That future lock is composite: execution plans + control protocol + harness + memory + authorization. Authoring it follows the monorepo's role-separated protocol (`docs/reviews/AGENT-REVIEW-PROTOCOL.md`) — none of the inputs below shortcut that.

## Standing constraints the lock inherits

- Layer split: orchestration policy never stores; storage never decides (control-plane ADR 0033; memory design §2).
- Q4 persona constraint (decision-log 2026-07-17): no user profiling; local-first, consent, provable erasure.
- Hosted agent memory = platform data under monorepo `DATA-LIFECYCLE.md` / monorepo ADR-0002 (the memory design is scoped local-only and says so).
- No abstraction without a producer; contracts open when shapes are actually emitted (decision-log 2026-07-02).
